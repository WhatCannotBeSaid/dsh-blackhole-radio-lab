## 1. 复核：第三轮的「表分辨率不足」根因判断被推翻

第三轮报告 §1.3 断言：64×32 `inverse_radius` 表在近轴区 Δr≈0.05–0.10 世界单位，大于夹具半径 0.04，所以弧只剩两端。**这条不成立。**

同一 drawing-buffer 像素中心上三方对比（GPU 探针 mode 1/3/5/12/13 与 CPU 逐行镜像、CPU 独立积分）：

| 量 | 样本 | 平均 \|Δ\| | 最大 \|Δ\| | 最差点 |
| --- | --- | --- | --- | --- |
| e² | 7392 | 3.78e-6 | 7.31e-6 | (659,496) 0.099232 / 0.099225 |
| alpha | 7392 | 1.34e-6 | 4.15e-6 | (599,520) 3.091148 / 3.091144 |
| delta | 7392 | 4.48e-6 | 5.83e-6 | (696,502) 2.975707 / 2.975701 |
| 偏折角 | 7392 | 5.70e-5 | 1.97e-4 | (623,494) 1.514519 / 1.514322 |
| u1（第二交点） | 7392 | 2.35e-5 | 8.12e-5 | (661,497) 0.328653 / 0.328572 |
| u0（第一交点） | 0 | — | — | 该区域 u0 全为 −1，与 oracle 一致 |

表解码误差在 1e-5 shader 量级，换算世界单位 ~1e-5；夹具半径 `geom.z` = 0.04/RS = 0.1039 shader。误差比半径小四个数量级——**表解码（分辨率 + 量化 + 双线性插值）不是弱场与近轴弧的根因**。

方法教训（保留，以免重犯）：最初的镜像把轨道平面结点方位角 `alpha` 当成了 `delta`，于是得出「交点整体偏 6 px、弧被截成 46 px」的假象。`alpha = acos(dot(eXPrime, tAxis))`，`tAxis = normalize(cross(eZ, eZPrime))`，且当 `dot(tAxis, eYPrime) < 0` 时取反。修正后镜像与 oracle 逐像素重合（`x=640,y=514`：oracle r=1.5954、mirror r=1.5962 世界单位；dist 0.0046 vs 0.0038）。凡「GPU 与 CPU 不符」的结论，先验证镜像用的是真实 `alpha`。

## 2. 首个出现偏差的环节

链路与判定：

1. shader 求交（`traceRay` + 两张表）→ **与 oracle 一致**（上表）。
2. 交点出屏 (u0/u1)、槽位、`crossingIndex` → **一致**（弧区 slot2 / crossing 1、2）。
3. 逐像素 ID 归属（`cov >= 0.5`）→ **弱场在此处必然失败**（见 §3）。
4. 组件提取（bbox、面积质心）→ **上弧组件质心落在弧的凹陷里**。
5. 锚点门控 `radioIdAt(blob.x, blob.y)` → **首个偏差就在这里**：用组件面积质心去查 id，凹形弧的质心不在弧上，返回 null，整个组件被丢弃。
6. 锚点位置与点击 → 连带失效。

第 5 步的实测：上弧 304 px 组件的面积质心是 buffer (640, 510.57)，而弧在 x=640 只占 y=513–515（`floor` 到 510 落在凹陷），门控 `hit === null`，于是 304 px 的弧被整条丢掉；下弧 266 px 同理。存活下来的只有 5 个单像素孤岛——这正是第三轮看到的 `near-axis anchor count 5`、位置偏 68–70 px、`strip w=1 h=1`、`+1 px null` 全部现象的来源。

## 3. 弱场源：交点正确，输在覆盖判据与参考口径

- 交点存在且正确：r=4.1996 世界单位、φ=1.6047、`crossingIndex=1`、`slot=2`，与 oracle 一致。
- 像的真实几何：连续像仅 **0.5 px 厚 × 3.5 px 长**。该处径向尺度 0.267 世界单位/px（盘面近侧视压缩约 26 倍），`R = 0.04` 世界单位只能覆盖 ±0.15 px。像素中心距轨迹最近也有 0.088 世界单位，`cov = (0.04−0.088)/max(wRadial,1e-6)+0.5 ≈ 0.13`。
- 因此 `cov >= 0.5` 在该源上**数学上不可能成立**：14 个像素的 cov 落在 0.046–0.302，无一过半。这是判据与像尺度不相容，不是阈值调参能解决的，也不是交点错误。
- 冻结参考本身是「逐列求 r=r_s 的根、再按 |arc| ≤ 0.04 过滤、最后对命中列取 py 均值」的**曲线测量**：118 个候选列中只接受 3 列（x=1177/1178/1179，py=361.68/361.83/361.98）。它描述的是光线轨迹与源心圆的精确相交，不是栅格化后的像素归属。

## 4. 修改内容

### 4.1 `src/scene/geodesic.glsl.js`（求交不变，改归属与探针）

- 归属改为「像素单元与发射圆盘是否相交」的**触及面积**：8×8 平行四边形子采样
  `q = p + off.x*dxp + off.y*dyp`（`gvec2 off = (vec2(a,b)+0.5)*0.125 - 0.5`），`idCov = hits/64`，`attributed = idCov >= 0.25`。
  方向向量取 `dFdx/dFdy` 的**真实交点位置**，而不是把 `wRadial/hTangential` 当各向同性半径用。
- `dFdx/dFdy` 必须在非一致控制流之外取值：`vec2 i1s = crossDir1.xy / max(u1,1e-6)`、`i0s` 同，`dxp1 = dFdx(i1s)` 等全部提到 `if (u1 >= 0.0)` 之前（否则 quad 内分支不一致时导数是未定义值）。

指令给出的启用前提是「证实当前表误差超过夹具所需精度」。实测表解码误差 1e-5 shader，夹具半径 0.104 shader，弧质心与参考差 1.10/1.08 px，覆盖收敛 8×8 平均 0.0022——**前提不成立**，因此本轮不新增数值求交路径。若将来表被替换或夹具缩小到 1e-3 shader 量级，再按 §4 的守恒量参数化方案补。

3. **spec 自身矛盾**（需作者裁决，本轮未改 spec）：

## 10. 结论

- 根因：**不是**表分辨率，而是 ① 锚点用面积质心做 id 门控，凹形弧的质心不在弧上，整条弧被丢弃；② `cov >= 0.5` 在 0.3 px 厚的弱场像上必然 0 像素；③ 条带厚度用 bbox 高度度量，∩ 形弧必然 18 行。
- 首个偏差环节：`src/stage.js` 的锚点门控 `radioIdAt(blob.x, blob.y)`。
- 修法：触及面积归属（8×8 子采样、阈值 0.25）+ 代表像素门控 + 每列平均厚度 + 面积覆盖加权质心 + 命中与标签同源；GPU 求交路径未改、未新增数值求交。
- 通过项：59/59、13/13、DPR 2 与 1.5、197/197、69/69。
- 剩余：弱场行翻转 2.09 px/0.05°（欠采样极限）、参考口径系统差 ~1.1 px、spec 两条自相矛盾待裁决、GPU 计时不可用。
- 阶段二状态：**部分通过**（不进入完整电台目录阶段）。
